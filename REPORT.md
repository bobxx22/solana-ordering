# Report: how Solana validators order transactions inside a block

Status: **draft**. The main run has not been done yet. It is planned for the end of the measurement period, after
the design has been reviewed. Everything below comes from the committed raw data:

- the tables are regenerated by `node src/cli.ts analyze` into
  [`data/mainnet-beta/results/results.md`](data/mainnet-beta/results/results.md);
- `verify` checks every transaction against the chain. Last check: 183 landed transactions in 50 blocks, plus a
  sample of whole transactions for role parameters and every unlanded one; 0 problems.

## What we see so far (one or two trials per client; not conclusions)

1. **The delivery path decides everything.** Through the public RPC, the order of our transactions in the block
   followed the order in which the RPC released them. The RPC's response time stands in for the release time:
   - by release order, mean gamma 0.79 [0.57, 0.96], Holm p < 0.001;
   - by the fee rules, nothing significant;
   - landing delay correlates with the RPC response time at r = 0.95;
   - the RPC held five-transaction bursts for 1.3 s at the median, against 0.1–0.5 s for single transactions.

   Only 25% of the transactions reached the targeted leader. Delivered straight to the leader's advertised QUIC
   address, every transaction that landed did so in the targeted leader's window.
2. **Buffered bursts sit at the head of the block.**
   - Sent two slots before the window, the six landed in the window's first slot at 2–7% of the block.
   - Their order matched reward/cost exactly for AgaveBam (E A D C F B) and Firedancer (E A D C F B), almost for
     HarmonicFiredancer (A E D C B F) and HarmonicAgave.
   - It did not match for the two JitoLabs trials or for Rakurai.
3. **A burst inside the window.**
   - Firedancer again gave exactly the reward/cost order (E A D C F B), although its block was already being produced.
   - Agave placed all six on consecutive positions (112–117) in an order close to the send order.
4. **Streamed 30 ms apart:** arrival order dominated.
5. **Not every address takes direct unstaked traffic.**
   - In calibration 1, a JitoLabs and a FireBAM leader acknowledged the QUIC handshake but included nothing, although
     both produced every slot of their window.
   - In calibration 2 one JitoLabs address did not acknowledge any of the six streams.
   - The run now records per-stream acknowledgements (proof of delivery). It counts only trials that landed towards a
     client's quota, and stops targeting an address that drops two bursts in a row.

## What went wrong

| what | how we found it | what we changed |
|---|---|---|
| The public RPC held bursts ~1.3 s and released them in its own order, so the pilot measured the RPC, not the leader. | Round-1 reviews of the pilot; confirmed by recomputing (tau 0.845, p = 0.0001). | Direct QUIC delivery to the leader's advertised TPU address (`py/tpu_sender.py`). The pilot is kept as the comparison it became. |
| 7 of 22 pilot dispatch attempts were skipped as "missed slot": a `>=` instead of `>`, and signing too late. | Pilot log and ledger. | Fixed; skips are logged in `events.jsonl`; the design cell is consumed only on dispatch. |
| The pilot run crashed waiting 160 s for a rare client's window (fixed 120 s timeout), so the automatic collection did not run. | Pilot log. | Timeout proportional to the distance; collection runs after any error. |
| The block's fee-reward recipient is not always the leader: some validators collect block revenue in a separate account. | QUIC feasibility test: two blocks in the targeted window paid fees to non-validator accounts. | The leader is the slot's scheduled leader (`getSlotLeaders`); the fee recipient is stored separately. |
| BAM and Harmonic validators advertise shared gateways: 364 AgaveBam validators on 17 addresses, 86 Harmonic validators on 6 hosts. "Direct to the leader" is direct to a gateway for them. | Round-2 reviews; confirmed from the snapshot. | Ingress host recorded per trial; statistics resample hosts; drops are counted per address; README frames BAM and Harmonic as pipelines. |
| reward/cost and price per CU disagreed on one pair only. | Round-1 reviews. | Role F (A with a 64 MiB loaded-data limit): same price and fee, 8× the cost. |
| The rebuilt "scheduled cost" of other transactions ignored the loaded-data limit, the very term F tests. `meta.costUnits` counts bytes actually loaded. | Round-2 reviews. | Cost rebuilt from first principles (signatures and precompiles, write locks, data, requested CU limit, requested loaded-data limit, 64 MiB by default). A test checks it equals the design cost for all six roles. |
| Spend-cap gaps: reservations released on a send error or after 20 s; sweep could be refused at the cap; two processes could spend at once. | Round-1 reviews (no overspend happened: the ledger matches the balances). | Reservations close only on landing or proven expiry (and `getTransaction` must also know nothing); sweep allowance; exclusive, host-aware ledger lock that re-reads the ledger; genesis-hash check. |
| One payer set would never have been topped up during a long run (`trial % 10 === 0` always picks the same set), which would have shown up as false "drops". | Round-2 review. Not triggered yet: the runs were short. | Before every trial the set about to be used is checked and topped up while idle. |
| A trial split over two blocks counted as two units; the shared/independent factor was not analysed. | Round-2 reviews. | One unit per trial, ordered by (slot, index) within the targeted window; decisive pairs reported per delivery and mode. |
| The QUIC sender reported success without proof of delivery, and the process could hang 10 s on exit. | Round-2 reviews. | Per-stream acknowledgement times, blocked-stream flags and connection state are recorded; close timers per address; clean shutdown. |
| A dry run signed with the funded keys when they existed. | Round-2 review. | Dry runs always use throwaway keys. |
| Free Helius plan: 1 sendTransaction/s and no staked connections; free dRPC does not serve mainnet. | Provider documentation; probe. | Helius is used for reads only. |
| Docker Desktop cannot run on the author's Windows build (virtualization components missing). | Installer error. | The image is built and run in GitHub Actions on every push. |

## Main run (to come)

two other deliveries, and both modes. That is at most 61 000 lamports per landed trial, under the 0.05 SOL cap.
The local-scheduler labels (Agave, JitoLabs, Firedancer, Rakurai) carry the client comparison; BAM and Harmonic are
reported as pipelines.
